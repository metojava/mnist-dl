17 - Optimizing for Performance

Concrete levers in this codebase - from micro (Tensor) to macro (Trainer) - with where to look (file:line) and how much each matters.

Batch 64-256Sweet spot: amortizes matmul overhead vs cache
Clip 5.0 + LR 1e-3Lets you use larger LR without divergence
Dropout 0.2-0.3Regularizes without halving throughput

1. Tensor parallelism (ml/core/Tensor.java:7)

  • PARALLEL_THRESHOLD=50_000 and MATMUL_PARALLEL_OPS=2_000_000 gate sharding via ThreadPoolManager.compute(). Keep tensors above threshold to benefit; tiny batches (e.g., 1-8) stay sequential and are slower per sample.
  • Matmul tiling: Tensor.matmul shards by output rows via CompletableFuture. For 784->256, batch 256 gives 256*256*784 ~51M ops -> parallel. Batch 32 is ~6M -> still parallel but less scaling.
  • Reductions: sum/max/mean/sumCols use lock-free accumulators - no ReentrantLock contention.
// Good: large batch amortizes fork/join
Tensor out = Tensor.matmul(batch256, W.transpose()); // parallel
// Bad: loop over single samples
for(row) out = Tensor.matmul(singleRow, W.transpose()); // sequential overhead

2. DenseLayer caching (ml/layer/DenseLayer.java:18)

  • cachedTranspose avoids re-transposing W each forward. invalidateTranspose() only after update - forward is 2x faster.
  • Bias addition is sharded if output > 8192. BiasGrad via sumCols is also parallel sharded above threshold.
  • Grad accumulation shards by batch chunk into thread-local partialDW then merge - avoids atomics.
Pattern: keep in * out * batch large enough to shard, but not so large that GC pauses from allocating partialDW arrays.

3. Trainer loops (ml/training/Trainer.java:35)

  • DataLoader shuffle is O(n) Fisher-Yates via ThreadLocalRandom - run once per epoch, not per batch. NoDataLoaderBench shows ~5-10% speedup by skipping it, but loses generalization.
  • fitParallel overlaps forward passes via pool, but backward stays sequential (network stateful). Use when forward dominates (deep CNN/Transformer).
  • EarlyStoppingTrainer clones Dense weights via System.arraycopy - cheap vs re-training.

4. Data pipeline

  • MNISTLoader loads whole dataset as one Tensor (60k*784 doubles ~ 376 MB) - fits in L3? Keep as Tensor, sliceRows for batches (zero-copy-ish via System.arraycopy into new Tensor). Avoid per-sample file I/O.
  • ImageReader for CIFAR-100 resizes to 32x32 once at load; not per epoch.
  • BoW in Vocab builds dense double[] - sparse would be faster for large vocab, but dense wins for <5k vocab due to contiguous matmul.

5. Regularization & augmentation cost

  • Dropout forward allocates mask and scales - disabled when training=false (inference 20% faster).
  • WeightDecay loops over all weights - O(params) per step - negligible vs matmul O(batch*params).
  • GradientClipper by NORM computes global L2 then scales - O(params) extra pass; by VALUE is also O(params) but cheaper branch.
  • RandomFlip/Rotation are Layer impls - they run on CPU per row; place first and only when needed (vision) else skip.

6. Optimizer choice

OptimizerStep costWhen fastest
SGDO(params)Large batch, no adaptivity - cheapest
SGD+momentumO(params) + velocitySimilar, momentum adds one pass
Adam/AdamW~4x SGD (m,v,bias-corr)Needs fewer epochs to converge - net win despite per-step cost
RMSProp/AdaGrad~2x SGDSparse features - AdaGrad cache grows, consider Adam instead
Rule: Adam 0.001 converges in ~10 epochs where SGD 0.1 needs 30+ - 3x fewer passes offsets 4x per-step cost.

7. LR scheduling (ml/training/LRScheduler.java:1)

  • CosineAnnealing and WarmupCosine avoid late-epoch thrashing - no extra compute.
  • ReduceOnPlateau checks val loss - one forward per epoch on val set, negligible.
  • StartAutoUpdate uses ScheduledExecutorService - avoid busy-wait loops.

8. Evaluation (ml/evaluation/Evaluator.java:1)

  • Parallel evaluate shards batches and merges ConfusionMatrix - near-linear scaling with cores for large test sets (>10k).
  • Use predictBatch for inference - one matmul per 256 vs 256 matmuls of single rows is 10-20x faster.

9. Practical checklist

  1. Batch 128-256 for MNIST/Fashion, 32-64 for LSTM (seqLen large).
  2. Use SeedManager.setSeed(42) to make timings comparable.
  3. Profile with the examples/*Bench files: MinimalBench isolates matmul, DiagBench checks grad health, BenchEpoch times real training.
  4. Keep network width moderate: 784-512-256-128 is ~500k params, matmuls dominate; 784-2048 would be 1.6M and GC-heavy.
  5. Reuse Tensors where possible: applyInPlace, multiplyInPlace avoid allocation.
  6. Save models via binary (saveModel) - JSON is 5x larger and slower to parse.
