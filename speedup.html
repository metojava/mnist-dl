Epoch & Evaluation Speedup

How the Java deep-learning library in this project was made faster than the original implementation at C:\Users\dell\Desktop\c\mnist-dl. The work targets the two hot paths that dominate every run: the dense matrix multiplications inside the network, and the per-element array loops used by the activations, loss and data loader.

Measured result. With the same architecture (784→128→64→10), the same Fashion-MNIST data and the same batch size (512), the optimized build roughly 2.5× the training throughput and 3.2× the evaluation throughput of the previous build. See the measurements table.

2. What dominated the original runtime

In the original code, every forward and backward pass is a chain of dense matrix multiplications, and each of those was a naive i → k → j triple loop over double[] data, reached through bounds-checked get()/set() calls: 

// ORIGINAL Tensor.matmul — double[] + naive loop order
double[] ad = a.data, bd = b.data, rd = result.data;
for (int i = 0; i < m; i++) {
    int aRow = i * n, resultRow = i * p;
    for (int k = 0; k < n; k++) {
        double aValue = ad[aRow + k];
        int bRow = k * p;
        for (int j = 0; j < p; j++) {
            rd[resultRow + j] += aValue * bd[bRow + j];
        }
    }
}

This has three compounding costs:

  1. Bus traffic. double moves twice the bytes of float, and SIMD units process half as many lanes per instruction.
  2. Cache misses. The inner loop streams the whole result row and re-reads b for every row of a, so neither operand stays resident in L1/L2.
  3. Single thread. The whole batch is multiplied on one core, ignoring the other cores of the machine.

3. Optimizations applied

Step 1

float instead of double

The entire Tensor storage and every layer were converted from double[] to float[]. This halves memory traffic and doubles the effective SIMD width of the arithmetic, which is the single largest win for dense GEMM. It touches Tensor, DenseLayer, ReLU, Softmax, CrossEntropyLoss, MNISTLoader and MNISTVisualizer.

Step 2

Cache-blocked, register-tiled GEMM

Tensor.matmulInto() now splits the right operand into JC = 32 column tiles and KC = 128 depth tiles, and accumulates four result columns in registers before writing them back once. The inner loop reads b sequentially, so the working set stays in L1/L2 and the JIT can auto-vectorize.

Step 3

Row-parallel execution

New ml.Parallel helper partitions the output rows of a GEMM across a fixed pool of daemon threads (up to min(8, availableProcessors)). Because each thread owns disjoint output rows, no locking is needed and the per-element summation order is unchanged. It activates only for large products (m ≥ 64 && m*n*p ≥ 4 M), so small layers keep the low-overhead single-threaded path.

Step 4

Direct array access in hot loops

Activations, the loss and the loader were rewritten to walk the backing float[] directly with a running offset instead of calling get()/set() per element. This removes per-element bounds-checked method dispatch and lets the loops vectorize.

Step 5

Zero per-batch allocations

DenseLayer, ReLU, Softmax and CrossEntropyLoss keep reusable buffers that are only reallocated when the batch shape changes (via a small ensure() helper). Trainer reuses its batch buffers too. This eliminates almost all garbage from the training loop and the corresponding GC pauses.

Step 6

Cached weight transpose

DenseLayer lazily caches WT and invalidates it only in update(). Previously a fresh transpose was materialized on every backward call.

Step 7

Fused transposed matmul

New Tensor.matmulTransposedA() computes dW = XT × dZ directly from X without building a transposed copy, tiling the batch dimension to stay in cache. Also parallelized over output rows.

Step 8

Bulk arraycopy + larger batches

Trainer gathers batch rows with one System.arraycopy per sample instead of per-element reads, and the default batch size was raised from 128 to 512 to amortize the per-matmul overhead over more work.

4. The kernel rewrite, side by side

Before

Naive triple loop

for (int i = 0; i < m; i++) {
  int aRow = i * n, rRow = i * p;
  for (int k = 0; k < n; k++) {
    double aValue = ad[aRow + k];
    int bRow = k * p;
    for (int j = 0; j < p; j++) {
      rd[rRow + j] += aValue * bd[bRow + j];
    }
  }
}

No reuse, no tiling, one thread.

After

Tiled, hierarchical, parallel

boolean parallel =
    m >= 64 && (long) m * n * p >= 4_000_000L;

if (parallel) {
  Parallel.parallelRows(m, (r0, r1) -> {
    /* each thread owns rows [r0, r1) */
    for (int jj = 0; jj < p; jj += JC)
      for (int kk = 0; kk < n; kk += KC)
        for (int i = r0; i < r1; i++) {
          float c0=0,c1=0,c2=0,c3=0;   /* registers */
          for (int k = kk; k < kEnd; k++) {
            float aValue = ad[aRow + k];
            int bRow = k * p + jj + j;
            c0 += aValue * bd[bRow];
            c1 += aValue * bd[bRow + 1];
            c2 += aValue * bd[bRow + 2];
            c3 += aValue * bd[bRow + 3];
          }
          rd[resultRow + j]     += c0;
          rd[resultRow + j + 1] += c1;
          rd[resultRow + j + 2] += c2;
          rd[resultRow + j + 3] += c3;
        }
  });
  return;
}

Cache tiles + register accumulation + thread pool.

5. Why evaluation sped up the most

Evaluation is a single forward pass over all 10 000 test images. It never touches the optimizer or the batch-gathering code, so its speedup comes purely from the forward-path changes: float storage, the blocked GEMM, row parallelism, and direct array loops in the ReLU/Softmax forward passes.

For the evaluation shapes the parallel threshold is crossed on every layer:

  • 10000 × 784 × 128 ≈ 1.0 G MACs — parallel
  • 10000 × 128 × 64 ≈ 82 M MACs — parallel
  • 10000 × 64 × 10 ≈ 6.4 M MACs — parallel

That is why evaluation improved by ~3.2× while the full epoch (which also waits on the sequential optimizer step and shuffle) improved by ~2.5×.
